# Astra 初步开发计划

**文档状态**：已确认的初步计划，阶段 1-6 已完成首轮执行验证，后续阶段按增量推进
**计划版本**：Initial Development Plan 0.2
**日期**：2026-11-05  
**适用范围**：Astra 最小本地 Runtime 的设计、实现和验证

本文将 Astra 当前已经确认的设计边界转换成开发顺序。它描述先做什么、为什么做、每阶段交付什么、怎样判断阶段完成，以及哪些事情明确延后。

本计划不冻结 Python 类名、目录结构、序列化格式或具体 API。具体接口必须在对应阶段根据用例和验证结果确定。

## 当前执行摘要

- 阶段 0 的设计、边界和验收基线已完成；
- 阶段 1-4 已完成首轮实现，包含最小 Kernel、日志、JSON 配置、可信离线插件和 Workflow Composition；
- 阶段 5 已完成取消、超时、权限、日志故障隔离和资源释放的最小闭环，但外部副作用幂等、资源限制和背压仍未实现；
- 阶段 6 已完成本地性能基线和回归验证，持续性能门禁、高并发和高速流专项验证仍未完成；
- 阶段 7 自动适配层继续保持在底座之外，暂不进入 Kernel。

当前实现细节和测试证据见 [`implementation-status.md`](implementation-status.md)；本计划保留完整的长期阶段目标，不把尚未实现的后续能力描述为当前承诺。

## 一、总目标

Astra 第一轮开发的目标，是形成一个独立、最小、可验证的 Component Runtime，使开发者能够：

- 载入本地组件和插件；
- 让组件声明并提供稳定 Capability；
- 通过统一能力契约进行调用；
- 组织多条 Workflow 的串行、并行、路由、管道和事件协作；
- 让 Workflow 作为 Component 对外提供新的 Capability；
- 为每次运行提供明确的身份、作用域、生命周期和取消传播；
- 通过统一日志和诊断接口观察执行过程；
- 在能力缺失、权限拒绝、调用失败和资源清理时安全收束。

第一轮开发追求底座语义完整，不追求插件生态完整、配置管理完整或远程部署完整。

## 二、必须保持的设计约束

### 2.1 Kernel 保持最小

Kernel 只负责通用运行机制：

- Component 注册、启动、停止和释放；
- Capability 声明、查询、解析和绑定；
- Workflow Run、Invocation、Scope 和父子关系；
- 取消、超时、资源所有权和清理；
- 权限执行边界；
- 统一日志数据入口和基础诊断。

Kernel 不理解具体模型、Prompt、Memory、Agent、Persona、平台或设备业务。

### 2.2 Plugin 是装载和分发单位

Plugin 可以包含普通 Component、Capability、Workflow、配置和依赖。Plugin 负责被发现、校验、离线载入和启停；Runtime 最终仍然通过 Component 和 Capability 工作。

Workflow 可以被包装成 Workflow Component，并作为 Plugin 的一部分被载入。Plugin 管理不直接决定某条消息采用哪一条业务流程。

### 2.3 JSON 作为运行配置和编排输入

第一阶段使用简单 JSON 保存 Runtime 的外置配置和编排输入。它可以描述 API Key 或密钥引用、组件和插件启用信息、Capability 绑定、Workflow 选择、流程顺序、分支、并行关系、权限和运行参数。

JSON 由 Runtime 在启动时读取，也可以由未来的配置插件生成或修改。代码负责稳定的运行语义，JSON 负责当前应用采用哪些能力和流程组合。

密钥可以暂时保存在 JSON 中，但必须经过权限保护，并且不能进入普通日志、Trace、错误文本或事件数据。未来可以把 JSON 中的密钥字段替换为环境变量或安全存储引用。

第一阶段不实现配置编辑器、管理页面、用户级覆盖、复杂 Patch Layer 或 Profile 市场。未来这些功能可以作为独立插件加入。

### 2.4 一次运行内的组合保持稳定

一条消息创建 Workflow Run 后，使用的 Workflow Definition、组合快照和 Provider Binding 保持稳定。当前 Runtime 只允许在启动前应用配置，因此运行期间不会发生插件、配置或 Provider 替换；未来支持热更新时，这些变化才只影响新的 Run。

组合快照只是 Runtime 内部的不可变执行代际，不构成需要用户管理的 Profile 子系统。旧组合排空和释放属于后续 Generation 切换能力，当前实现尚未开放热更新。

### 2.5 统一日志数据，输出可替换

底座提供统一的结构化日志数据入口和访问接口。日志记录自动关联运行身份、组件、Workflow、Invocation 和 Scope。

控制台、文件、数据库、远程日志、日志检索和可视化都属于可以接入的日志组件。日志输出失败不能阻塞主流程；安全审计记录和普通调试日志需要保持不同的可靠性语义。

## 三、阶段总览

```text
阶段 0：需求和验证基线
    ↓
阶段 1：最小 Kernel、Workflow 基础与日志基础
    ↓
阶段 2：JSON 运行配置和编排输入
    ↓
阶段 3：离线 Plugin 载入
    ↓
阶段 4：Workflow Composition 扩展
    ↓
阶段 5：控制、安全和故障收束
    ↓
阶段 6：性能和稳定性验证
    ↓
阶段 7：外部模块自动适配层
    ↓
后续：管理界面、Profile、远程、DSL 和生态扩展
```

每一阶段都必须有明确的完成标准。阶段未完成时，不向下一阶段扩展复杂抽象。

## 四、阶段 0：需求和验证基线

### 目标

把当前设计转成可观察的最小用例，避免直接从抽象概念开始写大量代码。

### 主要工作

1. 固定 Component、Capability、Workflow、Workflow Run、Invocation、Scope、Stream、Event 和 Control 的词义。
2. 写出最小的无 LLM 组合场景：输入、路由、任务、记录。
3. 写出组件启停、能力替换、父子取消和资源清理场景。
4. 写出 JSON 配置、密钥保护、日志、错误、权限拒绝和迟到结果的观察要求。
5. 确定第一阶段不做的内容：远程、DSL、可视化、复杂 Profile、外部自动适配。
6. 设计基础测量方法，包括启动时间、调用延迟、流式间隔、取消响应和资源占用。
7. 确定第一版 Workflow 的最小语义：一个串行流程、一个路由分支和一个子流程调用。

### 交付物

- 最小场景清单；
- 术语和边界确认记录；
- 设计验收矩阵；
- 基础性能测量说明；
- 第一版开放问题列表。

### 完成标准

任何第一阶段公共概念都能对应到至少一个可观察场景；不再存在“需要支持但无法描述如何判断完成”的核心要求。

## 五、阶段 1：最小 Kernel 与日志基础

### 目标

先让 Runtime 能够安全地管理组件、能力、Workflow 和执行，不引入插件市场或复杂流程管理。

### 主要工作

1. 支持 Component 的注册、启动、停止和释放。
2. 支持 Capability 的声明、索引、查询和唯一解析。
3. 支持一次能力调用的请求、结果、错误和终态。
4. 支持 Run、Invocation、Scope 的身份和父子关系。
5. 支持取消、超时和资源清理。
6. 明确每类运行时状态的唯一 Owner。
7. 对缺失能力、版本不兼容和 Provider 歧义给出确定性失败。
8. 建立 Workflow Definition 和 Workflow Run 的最小关系。
9. 支持一个串行 Workflow、一个路由分支和一个 Workflow 子调用。
10. 建立统一的结构化日志数据入口。
11. 让日志记录自动关联执行身份和组件来源。
12. 提供最小备用日志输出，保证没有日志插件时 Kernel 仍然可诊断。

### 日志基础范围

第一阶段只实现日志数据的产生、关联、过滤和基础访问，不实现完整的日志平台。日志记录至少覆盖：

- Runtime 和 Component 生命周期；
- Capability 解析和调用；
- Run、Invocation 和 Scope 终态；
- 取消、超时和权限拒绝；
- 资源创建、释放和清理失败；
- 插件载入错误。

日志系统需要具备基本脱敏、长度限制和失败隔离能力。高频日志不能阻塞消息执行。

### 交付物

- 最小 Kernel Contract 文档；
- Component 生命周期验证；
- Capability Resolution 验证；
- Run / Scope / Invocation 验证；
- 基础日志数据契约；
- 统一日志访问说明；
- 初步错误和终态分类。
- 最小 Workflow 执行验证；

### 完成标准

- 两个不同 Component 可以提供同一 Capability；
- 调用方只依赖 Capability，不依赖 Component 内部实现；
- Scope 停止时能够释放其订阅和后台资源；
- 取消和超时可以被观察并最终收束；
- 最小 Workflow 可以完成一次串行调用、路由分支和子流程调用；
- 没有日志输出插件时仍能获得最小诊断信息；
- 日志故障不会直接导致主调用失败。

## 六、阶段 2：JSON 运行配置和编排输入

### 目标

让 Runtime 能够根据一个简单、可校验的 JSON 配置启动组件，并为 Workflow 提供当前运行所需的参数和组合关系。

### 主要工作

1. 描述启用的组件和 Workflow。
2. 描述 Capability 的绑定或选择。
3. 描述流程顺序、分支、并行关系和运行参数。
4. 描述基本依赖、权限和密钥字段或密钥引用。
5. 在启动前完成结构校验、依赖校验和敏感配置检查。
6. 生成一次不可变的组合快照。
7. 启动失败时拒绝进入半可用状态，并输出不包含密钥的诊断信息。
8. 允许未来插件生成或修改这份 JSON，但不在本阶段实现管理工具。

### 设计边界

Plugin Manifest 描述插件身份、包含的组件和能力、依赖与权限；JSON 选择当前启用哪些对象、如何绑定能力、怎样组织 Workflow 以及使用哪些参数。JSON 不能覆盖 Capability 契约，也不负责插件包的发现和安装。

最终的运行启动顺序应当能够解释为：发现并载入可信组件或插件，读取并校验 Manifest，读取并校验 JSON，解析 Capability 绑定，生成不可变的 Composition Generation，再启动本次组合。实现阶段可以分别开发这些步骤，但不能让 JSON 绕过插件契约或让消息热路径重复执行它们。

JSON 只表达“当前要运行什么组合和参数”，不负责：

- 保存所有运行时状态；
- 记录每条消息的执行过程；
- 管理插件安装历史；
- 取代 Workflow 的运行语义；
- 直接描述组件内部实现。

### 交付物

- JSON 配置和编排语义说明；
- 启动校验规则；
- 密钥保护和脱敏规则；
- 组合快照说明；
- 启动失败和诊断场景；
- 一个最小本地 Application 组合。

### 完成标准

Runtime 可以从一份 JSON 启动最小组件组合，并且在配置不完整、能力缺失、依赖冲突或敏感配置不安全时给出明确失败原因。

## 七、阶段 3：离线 Plugin 载入

### 目标

让本地插件成为 Component 和 Workflow 的可载入分发单位。

### 主要工作

1. 发现本地插件目录或已安装包。
2. 读取并校验插件的基本描述。
3. 识别插件包含的 Component、Capability 和 Workflow。
4. 检查本地依赖和版本约束。
5. 以注册事务方式完成载入，失败时回滚。
6. 管理插件启动、停止、排空和释放。
7. 确保插件注册的能力、订阅、任务和资源可以完整回收。
8. 允许一个插件包含多个普通 Component 和 Workflow Component。
9. 支持日志组件作为普通插件接入统一日志数据接口。

第一阶段只支持可信的本地进程内插件。在线安装、包管理、沙箱、跨进程隔离和不可信代码执行不进入本阶段。

### 交付物

- 最小 Plugin Manifest 说明；
- 本地插件发现和载入流程；
- 依赖检查和冲突处理说明；
- 插件失败回滚场景；
- 插件停止和排空场景；
- 一个包含普通 Component 和 Workflow Component 的离线插件示例。

### 完成标准

- 插件可以离线载入并注册能力；
- 插件启动失败不会留下半注册状态；
- 插件停止后能力、订阅和后台资源能够回收；
- 新插件不会破坏已经开始的 Workflow Run；
- 日志输出插件可以通过统一接口接收运行数据。

## 八、阶段 4：Workflow Composition 扩展

### 目标

在阶段 1 的最小 Workflow 语义之上，验证开发者可以通过多个 Workflow 构建更复杂的消息流程。

### 第一批验证 Workflow

- 输入处理 Workflow：接收并规范化输入；
- 对话 Workflow：提供普通结果和流式结果；
- 任务 Workflow：执行多步骤任务；
- 记录 Workflow：订阅事实并记录结果。

### 主要工作

1. 支持 Workflow 作为 Workflow Component 对外提供 Capability。
2. 支持多个 Workflow 之间的串行调用。
3. 支持一个 Workflow 启动多个并行子 Workflow。
4. 支持路由分支和条件选择。
5. 支持有序的数据管道和流式传递。
6. 支持事件触发独立的 Workflow Run。
7. 支持至少一种明确的子任务结果汇合策略。
8. 支持结构化上下文贡献，由消费方决定如何使用。
9. 支持明确的失败、取消和迟到结果处理。
10. 保持 Workflow 内部实现与外部调用契约分离。

### 交付物

- Workflow Composition 设计说明；
- 串行和并行场景；
- Route、Pipeline、Stream 和 Event 场景；
- 子任务合并和失败传播场景；
- Workflow Component 插件示例；
- 组合流程的 Trace 示例。

### 完成标准

开发者可以只依赖公开 Capability 组合出新的 Workflow；一次 Run 内的 Workflow Definition、启动组合和 Provider Binding 保持稳定；所有跨 Workflow 的关系都能够通过调用、流或事件解释。

## 九、阶段 5：控制、安全和故障收束

### 目标

让 Runtime 在异常、权限和资源压力下仍然能安全结束，而不是只在正常路径上运行。

### 主要工作

1. 第一阶段必须先明确取消、停止和超时的适用范围，并验证父 Run 到子 Run 的取消传播。
2. 验证子 Run 脱离父 Scope 成为长期任务的条件。
3. 在 Provider 执行前完成权限判断。
4. 区分纯计算、受 Runtime 管理的资源和外部副作用。
5. 防止不安全的外部副作用被自动重放。
6. 限制并行子任务、流缓存、队列和后台任务数量。
7. 处理组件启动失败、后台任务异常和日志输出故障。
8. 确认停止流程能够排空运行、释放资源并写入最终状态。

暂停、恢复、审批、重试、组件健康状态和 Runtime 降级状态先形成候选设计；除非最小用例证明它们是底座必需，否则不作为本阶段实现前提。

### 交付物

- 控制语义说明；
- 权限和副作用验收场景；
- 故障隔离和资源收束说明；
- 资源限制和背压说明；
- 统一停止和清理流程；
- 安全审计记录范围。

### 完成标准

权限拒绝不会执行 Provider；取消能够传播并最终结束；资源能够释放；日志和诊断故障不会破坏主执行；外部副作用不会被隐式重试。

## 十、阶段 6：性能和稳定性验证

### 目标

验证底座自身的开销可测量、行为可重复，并且高频执行路径不会因为通用机制失控。

### 主要工作

1. 比较直接本地调用和 Capability 调用的开销。
2. 比较串行、并行和流式 Workflow 的开销。
3. 测量首次调用和后续调用的差异。
4. 测量取消响应、资源释放和日志写入的延迟。
5. 验证日志采样、限流和队列满时的行为。
6. 验证高并发 Run 和高速 Stream 下的稳定性。
7. 确认插件发现、依赖解析和启动逻辑不重复进入消息热路径。
8. 检查 Trace、权限和事件机制的额外开销。

### 交付物

- 性能测量结果；
- 基线与预算说明；
- 高并发和高速流验证结果；
- 热路径优化记录；
- 未解决的性能限制。

### 完成标准

关键路径的额外开销在预算内；调用、流、取消、日志和资源清理行为可以重复；发现问题时能够定位到具体 Runtime 机制。

## 十一、阶段 7：外部模块自动适配层

### 目标

在底座已经稳定以后，设计自动发现、扫描和生成插件壳的适配流程。

### 主要工作

1. 发现外部模块、类、函数、入口和元数据。
2. 判断目标模块的可调用入口和输入输出。
3. 推断或要求补充 Component 和 Capability 描述。
4. 生成适配外壳。
5. 补充生命周期、依赖、权限、错误和流式语义。
6. 生成 JSON 组合结果或插件描述。
7. 通过统一验收场景验证适配结果。
8. 允许手工修正自动生成的描述。

### 适配范围

未来可以用于：

- 外部项目的模块、Agent 和 Workflow；
- 社区插件；
- 其他符合条件的 Python 模块。

自动适配层属于底座之上的独立系统。它不能要求 Kernel 理解外部项目的领域类型，也不能改变底座的核心契约。

### 完成标准

至少有一个小型外部模块可以被发现、包装、注册和运行；生成的 Component 和 Capability 能通过与手工组件相同的生命周期、权限、错误和调用验收。

## 十二、后续阶段

以下内容等最小底座稳定后再安排：

- JSON 配置的编辑和管理插件；
- Profile 和 Application 管理插件；
- 日志查看和分析界面；
- 远程 Component Host；
- 持久化任务和可靠事件；
- Workflow IR、DSL 和可视化编辑器；
- 热重载和更复杂的版本管理；
- 更完整的插件生态和目录服务。

## 十三、阶段依赖关系

```text
阶段 0
  └─ 阶段 1
       ├─ 阶段 2：JSON 运行配置
       ├─ 阶段 3：离线 Plugin 载入
       └─ 阶段 2 + 阶段 3
              └─ 阶段 4：Workflow Composition 扩展
                    └─ 阶段 5：控制、安全和故障收束
                          └─ 阶段 6：性能和稳定性验证
                                └─ 阶段 7：外部模块自动适配层
```

阶段 2 和阶段 3 可以在 Kernel 基础可用后交叉推进，但 Workflow 组合验证必须建立在稳定的调用、Scope 和生命周期语义之上。

阶段 7 不能提前成为 Kernel 的设计前提。自动适配需要等底座的公共契约稳定后，才能验证它是否能够可靠生成。

## 十四、整体完成判断

初步开发计划完成的判断，不是所有未来功能都已经实现，而是：

1. 最小 Runtime 可以独立启动和停止；
2. 本地组件和插件可以被发现、载入和释放；
3. Capability 可以被稳定解析和调用；
4. 多 Workflow 可以串行、并行、路由、管道和事件协作；
5. Workflow 可以作为 Component 和 Plugin 对外提供能力；
6. 一次运行的组件绑定、生命周期和资源归属清楚；
7. 日志和诊断可以统一获取，且不会破坏主流程；
8. 取消、权限、错误和外部副作用能够安全收束；
9. 底座的行为和开销可以测量；
10. 外部模块适配可以作为独立插件在底座之上实现，但它不属于最小底座的完成条件。

## 十五、执行原则

- 先验证语义，再增加抽象；
- 先完成最小底座，再设计自动适配；
- 先使用 JSON 作为简单运行配置和编排输入，再考虑配置管理；
- 先提供统一日志数据接口，再扩展日志存储和展示；
- 先固定一次 Run 的组合，再讨论热更新；
- 让高频数据留在所属组件内部；
- 任何公共契约变更都要记录需求、影响、Owner 和验证方法；
- 没有明确用例和验收标准的功能，不进入当前阶段。
