# Astra 文档规划

文档先于实现，用来固定项目边界、统一概念并记录仍需验证的决策。设计原则和实现细节分开记录，避免在没有用例和测试依据时过早冻结复杂 API。

## 文档层次

| 文档 | 作用 | 稳定性 |
|---|---|---|
| `vision.md` | 定义项目目标、核心思想和成功标准 | 长期基线 |
| `boundaries.md` | 定义责任边界、明确禁止事项和第一阶段范围 | 长期基线 |
| `terms.md` | 统一 Component、Capability、Workflow 等词汇 | 公共词汇 |
| `roadmap.md` | 规划文档工作、验证工作和延期方向 | 阶段性 |
| `implementation-status.md` | 记录已实现范围、验证结果和下一步工作 | 实现状态 |
| `config-and-plugin.md` | 说明 JSON 运行配置和可信离线插件的首轮行为 | 实现说明 |
| `decisions/` | 记录需要长期追踪的架构选择 | 决策记录 |
| `reference/` | 保存外部参考资料和输入原文 | 参考资料 |

## 文档状态

使用以下状态区分结论强度：

- **原则**：项目方向或边界，短期内不应因局部实现方便而改变。
- **已决定**：已经选择的方案，但仍需要实现验证。
- **待验证**：已有候选方案，尚未通过用例或测试确认。
- **暂缓**：明确不进入当前阶段，未来由新需求重新提出。
- **参考**：来自其他项目的经验，不构成本项目约束。

## 文档变更规则

1. 新增公共概念时，说明它解决的问题、拥有的状态、生命周期和验证方式。
2. 讨论实现时，先说明对应的边界和用例，不以未来扩展作为唯一理由。
3. 任何公共契约变更都要记录影响范围和未验证内容。
4. 文档中的示例是语义示例，除非明确标注，否则不代表已经冻结的 API。
5. 引入参考项目的思想时，记录借鉴点，不默认复制其代码、类型或运行架构。
